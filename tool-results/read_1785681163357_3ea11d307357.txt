    30→## 1. Architecture Audit
    31→
    32→### 1.1 Current architecture
    33→
    34→RestoPanel is a **single-route SPA** running on Next.js 16 App Router, but using none of App Router's strengths beyond lazy chunking. The entire authenticated application is rendered by one React tree:
    35→
    36→```
    37→src/app/page.tsx                ← single root route (84 lines)
    38→  ├─ <Landing/>                 ← marketing site
    39→  ├─ <AppShell/>                ← dashboard chrome + sidebar + top bar
    40→  │    └─ <SectionRenderer/>    ← React.lazy() per section
    41→  ├─ <AuthDialog/>              ← client-only "auth"
    42→  └─ <Footer/>
    43→```
    44→
    45→The four functional API routes are isolated islands; no section of the dashboard actually calls them. **The dashboard is, today, a navigable click-through demo** — every screen reads from in-file mock arrays, not from Prisma.
    46→
    47→### 1.2 State management
    48→
    49→- **Zustand** (`src/components/rp/app/nav-store.ts`, 109 lines) is the only global store. Holds `view`, `section`, `org`, `location`, `authOpen`, `authMode`, `user` (a plain object, no JWT, no server session).
    50→- Per-section state is local React `useState`. There is **no server state** layer (no React Query for server data; TanStack Query is installed but unused for the dashboard).
    51→- Sidebar pinning uses raw `localStorage` (`rp-sidebar-pinned`). Pricing toggle persists `rp-pricing-annual`. No abstraction.
    52→
    53→### 1.3 Routing
    54→
    55→There is no nested route segment under `src/app/`. The whole dashboard lives behind one URL (`/`). This is fine for a demo but **disqualifying for production**:
    56→- No deep-linking to a section (e.g. `/app/reservas/abc123`)
    57→- No SSR / no streaming — first paint always blocks on the full client bundle
    58→- No per-route middleware (auth, tenant resolution, locale)
    59→
    60→### 1.4 Build config
    61→
    62→`next.config.ts` (12 lines) is the single most concerning production blocker:
    63→
    64→```ts
    65→const nextConfig: NextConfig = {
    66→  output: "standalone",
    67→  typescript: { ignoreBuildErrors: true },  // ← ships broken typecheck to prod
    68→  reactStrictMode: false,                    // ← disables React's dev safety net
    69→};
    70→```
    71→
    72→`ignoreBuildErrors: true` means the 41 TypeScript errors below **do not block the production build**. This is acceptable during the demo phase (every prior worklog entry relied on it) but must be flipped off before any real customer is onboarded.
    73→
    74→### 1.5 Module count — claim verification
    75→
    76→The task brief mentioned **"42+ modules"**. The lazy map wires up **41 sections**, with the `Section` type declaring **57** ids. The 16 unrendered declarations are `qa-*` (15 internal QA scaffolding pages, not user-facing) plus `landing-dynamic` and `roi-calculator` (which live inside `<Landing/>` and are not sidebar entries). **Verified:** the "42+ modules" claim is accurate for user-facing sections.

   256→## 4. Performance Audit
   257→
   258→### 4.1 Code-splitting
   259→
   260→✅ **41 lazy-loaded sections** via `React.lazy()` + `<Suspense fallback={<SectionSkeleton/>}>`. Each section is its own JS chunk. This is good.
   261→
   262→❌ But: `app-shell.tsx` itself is **1581 lines** and statically imports 40+ lucide icons, the entire NAV manifest, the `AuthDialog`, the sidebar, the top bar, the command palette. The shell chunk is the largest single client-side asset.
   263→
   264→### 4.2 Bundle size — known issues
   265→
   266→- **`mermaid` (`^11.16.0`)** is a heavy dependency used only by `src/components/rp/mermaid.tsx`. If that component is statically imported anywhere in the shell, it pulls ~1MB into the initial bundle. **Verify** that `mermaid.tsx` is itself lazy-loaded.
   267→- **`@mdxeditor/editor`** (~600KB) — only used by AI knowledge editor; verify lazy.
   268→- **`react-syntax-highlighter`** (~500KB with all languages) — used by `api-explorer.tsx`; verify it uses `PrismLight` with registered languages only, not the full build.
   269→- **`sharp`** (`^0.34.3`) — correctly a server-side dep, fine.
   270→- **No `bundle:visualize`** configured in `next.config.ts`.
   271→
   272→### 4.3 Memory issues
   273→
   274→- `priceCache = new Map<string, Stripe.Price>()` in `src/lib/services/stripe.ts:39` is **module-level and unbounded**. In a long-running serverless instance this will leak memory across requests. Replace with a TTL'd LRU or move to KV.
   275→- Same pattern in `getStripe()` / `getResend()` (singleton clients) — fine, those are stateless.
   276→- `globalForPrisma.prisma` singleton in `src/lib/db.ts` — correct for Next.js hot reload in dev, correct for prod.
   277→
   278→### 4.4 Database
   279→
   280→- `prisma/schema.prisma` had only `User` + `Post` (the tutorial schema). **Replaced in this audit** with 51 production models. Run `bun run db:push` to materialise.
   281→- `DATABASE_URL="file:./dev.db"` — fine for dev, **must** be swapped to PostgreSQL (or Cloudflare D1) for prod.
   282→- `db.ts` logs `['query']` in all environments — **disable in prod** (`log: process.env.NODE_ENV === 'development' ? ['query'] : []`).
   283→
   284→### 4.5 No streaming, no RSC
   285→
   286→Every section is `"use client"`. There is no Server Component, no `loading.tsx`, no `error.tsx`, no `Suspense` for data fetching. First contentful paint on the dashboard will always block on the full client JS.
